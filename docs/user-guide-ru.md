# Руководство пользователя v2rayA

Как установить v2rayA, подключить первый узел и пользоваться каждый день.
Командная строка нужна только для установки; всё остальное делается в
браузере.

Рядом лежат документы для разработчика, на них даны ссылки там, где они
подхватывают тему: [running-from-source-ru.md](running-from-source-ru.md)
собирает этот репозиторий и доказывает, что он работает, а
[testing-on-a-real-machine-ru.md](testing-on-a-real-machine-ru.md) проверяет
по одной функции на машине, где v2rayA уже запущен.

## Установка

v2rayA — это два бинаря, версии которых должны совпадать: `v2raya` (сервис и
веб-интерфейс) и `v2raya_core` (ядро прокси). Пакеты ниже ставят оба сразу
вместе с описанием сервиса; точные команды для дистрибутивов — в
[README_ru.md](../README_ru.md#установка) репозитория.

После включения сервиса откройте в браузере **http://127.0.0.1:2017**. Если
браузер на другой машине, вместо `127.0.0.1` — адрес сервера с портом 2017;
предупреждение про регистрацию — в разделе [Первый запуск](#первый-запуск).

Есть и Docker-образ (описан в `install/docker/` репозитория). Все настройки
хранятся в каталоге данных; перед обновлением сделайте его копию (см.
[Резервная копия](#резервная-копия)).

## Первый запуск

### 1. Регистрация

Первая зарегистрированная учётная запись становится администратором; других
нет. В общей сети ограничьте доступ к порту 2017 **до** регистрации либо
привяжите сервис только к loopback. Забытый пароль сбрасывается командой
`v2raya --reset-password` при остановленном сервисе.

### 2. Импорт узла

На странице **Прокси** кнопка **Импортировать** принимает ссылки
(`vless://`, `vmess://`, `ss://`, `trojan://` и остальные, по одной в
строке), изображение с QR-кодом или адрес подписки. У подписок своя
страница; обновляются вручную или по расписанию.

Две детали про ссылки, которые стоит знать сразу:

- Ссылка VLESS может нести значение `encryption` нового формата шифрования.
  v2rayA проносит его от импорта до конфигурации; ссылка без него строит
  туннель, который сервер не сможет читать, поэтому редактируйте узел через
  редактор с сохранением, а не перепечатыванием ссылки.
- Ссылка XHTTP (`xhttp`) может нести `mode`, `x_padding_bytes` и объект
  `extra` в форме, которую пишут другие клиенты. Все три понимаются и
  попадают в те же настройки, что пишет редактор.

### 3. Подключение и проверка

Нажмите **Запустить** на панели. Приложения доходят до ядра через локальные
порты:

| Порт | Что это |
| --- | --- |
| `127.0.0.1:20170` | SOCKS5 **с вашими правилами маршрутизации** (единственный включённый по умолчанию входящий порт) |

Направьте браузер на порт 20170 (или пропишите его системным прокси) и
откройте сайт, показывающий ваш адрес. Затем откройте его же напрямую: два
адреса должны различаться. Если совпали — узел не везёт трафик; проверьте,
что ядро запущено и узел выбран, прежде чем трогать правила.

Почему правила видит порт 20170: каждый входящий порт несёт тег, а
правило срабатывает, только если тег порта есть в его списке:

```
                        тег порта           что ему соответствует
                        ─────────           ────────────────────
клиент ─► 20170 SOCKS ──► rule-socks ──► ВАШИ ПРАВИЛА ──► direct / proxy / block / group
   │                                     хосты узлов ──► direct (защита от петли)
   │
   └──► (опциональные обычные входящие порты SOCKS/HTTP/VMess ──► маршрут по умолчанию ──► proxy)
```

Поэтому дополнительные входящие порты, включаемые в **Настройки → Адреса
и порты**, означают «всё через прокси» (кроме хостов самих узлов — они
идут напрямую, чтобы туннель не пытался везти сам себя). Если исходящее
подключение по умолчанию — балансирующая группа, маршрут по умолчанию
балансирует между участниками, но пользовательских правил это не
касается — они там по-прежнему не действуют.

## Повседневное управление

### Узлы и подписки

Узлы правятся из своего меню (**Изменить**); сохранение хранит все параметры
ссылки. Там же узел удаляется. Подписка обновляется на странице
**Подписки**; режим рядом с расписанием решает, пойдёт ли само обновление
через прокси.

### Группы

Узлы используются через группы прокси. `proxy` есть всегда; остальные
создаются кнопкой групп в верхней панели. Узел вступает в группу из своего
меню, либо выделите несколько и выберите **Добавить в группу прокси**.
Группа с несколькими подключёнными участниками использует участника с
наименьшей измеренной задержкой, а при типе Random распределяет
соединения; меню узла на панели закрепляет одного участника, чтобы
группа использовала только его. У закреплённого участника нет
отказоустойчивости, сбалансированная группа обходит мёртвых участников.
В настройках группы задаются адрес и интервал проверки.

### Режимы маршрутизации

**Настройки → Режим разделения трафика для порта правил** решает, что
входящие порты с правилами и прозрачный прокси делают с трафиком: всё
через прокси, кроме allowlist, только blocklist через прокси или
собственные правила RoutingA. RoutingA описан в интерфейсе в **Документация → Правила
маршрутизации**.

Готовые наборы правил можно импортировать по URL, а не писать вручную:
**Настройки → RoutingA → Источник правил**. Панель показывает адрес,
последнюю отданную версию и — если индекс называет несколько наборов —
выбор, какой импортировать. Импорт заменяет правила, поэтому редактор
перезагружается и показывает то, что принёс источник. Повторный импорт той
же версии отвечает, что ничего не изменилось.

### DNS

**Настройки → Настройки DNS** перечисляет DNS-серверы: каким доменам каждый
отвечает и через какое исходящее подключение (`direct`, `proxy` или имя
группы). Правила точно так же импортируются по URL (**Источник правил** в
том же диалоге). Запросы обслуживаются на порту 52353; прозрачные режимы
направляют туда системный резолвер сами.

### Порты и общий доступ

**Настройки → Адреса и порты** меняет каждый входящий порт; `0` закрывает
порт. По умолчанию включён только SOCKS5 с правилами. Расшаривание
портов за пределы машины (общий доступ к порту, к LAN) открывает прокси в
сеть — защитите его пользовательским входящим портом с именем и паролем.

### Журналы

Страница **Журналы** показывает журнал сервиса; рядом переключатель на
журнал ядра. Когда что-то сломалось, воспроизведите один раз и читайте
журнал вокруг этого момента: каждое соединение пишет, через какое исходящее
подключение пошло, каждый DNS-запрос — какой апстрим ответил.

## Резервная копия

Все настройки — узлы, подписки, группы, правила, источники — лежат в одном
файле базы. Остановите сервис и скопируйте его:

```sh
sudo systemctl stop v2raya
cp ~/.config/v2raya/v2raya.db ~/v2raya-backup-$(date +%F).db
sudo systemctl start v2raya
```

Для восстановления остановите сервис, положите файл назад и запустите
снова. Обновление пакета настроек не трогает, но копия перед ним всё равно
нужна — от откатов не застрахован никто.

## Если не работает

| Симптом | Сначала проверьте |
| --- | --- |
| Страница не открывается | запущен ли сервис, тот ли порт |
| Ядро не запускается | выбран ли узел; свежий ответ — в журнале |
| Адрес через прокси равен прямому | узел не везёт трафик; чините узел, а не правила |
| Правила «не действуют» | клиент смотрит не на входящий порт с правилами (по умолчанию SOCKS5 20170) |
| Импорт набора роняет ядро | набор называет geo-теги, которых нет в geo-файлах |
| DNS не отвечает | какой апстрим и исходящее подключение у правила; спросите напрямую `dig @127.0.0.1 -p 52353 example.com` |

Полный разбор с командами — в [testing-on-a-real-machine-ru.md](testing-on-a-real-machine-ru.md), технические детали форматов — там же в разделе про источники.
